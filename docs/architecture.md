# Architecture

```
default/apps.json ────────────────┐
~/.ai-stackprint/apps.json ───────┴─> AppCatalog.Load() ──> List<AppDefinition>
                                                        │
 project folders (user picks) ──────────────────────────┤
                                                        v
                                   Scanner.Collect(defs, projects)
                                     ├─ detect folders      -> AppInfo (installed?)
                                     ├─ Roots / ProjectRoots -> skills (SKILL.md or flat *.md)
                                     └─ IPluginReader        -> plugins and extensions (+ their skills): pluginManifest, plugins[]
                                                        │
                                                        v
                                        ScanResult(Items, Apps) -> UI
```

## Data folder
`~/.ai-stackprint` on every OS (`DataFolder`): `settings.json`, `state.json`, `projects.json`, `apps.json`, `models.json` (your model changes; an older `prices.json` is moved into it on start and kept in `backups/`) at the top; `cache/` (scan-cache.json, last-scan.json, models.json: downloaded model data), `logs/` (crash.log, crash.seen, perf.log, perf-report.txt), `backups/configs/` (config files before a save) and `backups/skills/` (removed skills). `Program.Main` calls `DataFolder.Prepare` first: files of an older version (`%APPDATA%/AiStackprint`, or `~/.config/AiStackprint` on macOS and Linux; `AiProfiler` before that) are copied to their place and deleted, never over a file that is already there; the old folder keeps `MOVED.txt` listing anything left. Files that could not be copied stay and are tried again next start (a toast says so).
- Versions and defaults (`VersionedJson`, `JsonLayers`): each file has `"version"` (missing = 1). An older one is copied to `backups/<name>.v<n>.json`, upgraded one step at a time and written back; a newer one is read but never written (a toast says changes are not saved); a file that is not JSON is copied to `backups/<name>.broken.json` and the defaults are used. Writes go to a `.tmp` file, then replace the old one. `settings.json` holds only what differs from the built-in `default/settings.json` (every setting, its default and what it means; `SettingsStore.Defaults()`), and keeps keys this version does not know (`Settings.Extra`). `state.json` (`StateStore`, `UiState`): panel height, last update check, dismissed update; an older settings.json's values for these move there on load.

## Model data
- `default/models.json` (embedded in Core; schema `default/models.schema.json`): context window, max output, prices in USD per 1M tokens, long-context tiers (`above`), multipliers (`fast`, `us`), web search price, retirement date and successor, per model. A missing value is unknown, not free.
- Generated by `tools/ModelData` from LiteLLM's `model_prices_and_context_window.json` (MIT): chat models with text output from anthropic, openai, gemini, xai, deepseek and mistral; the provider prefix removed (`gemini/x` → `x`); dated copies with the same numbers dropped; one model per block, small objects on one line, so a weekly diff shows what changed. Checks (fail the run): schema fields and values, each provider present, at least 80% of the current count, at most 500 KB. Price changes over 10× are listed in the PR. The same models give the same file (date and commit kept), so an unchanged week opens no PR.
- `.github/workflows/models.yml`: Sundays 12:00 UTC and on demand; LiteLLM's latest commit for the file, downloaded at that commit; retries after 15, 45 and 90 minutes; on a change, force-pushes `bot/models-update` and opens or updates its PR. The repository must allow GitHub Actions to create pull requests (Settings › Actions › General).
- `ModelCatalog` (app): the built-in data, or `cache/models.json` when its `updated` is later (downloaded by `ModelDataUpdate` when Settings › Updates is on: at most daily with the update check, raw file with `If-None-Match`, 10 s timeout; version 1, a date and models with a provider, at most 2 MB, or it is not saved; the result and ETag are kept in `state.json`; the Usage page notes data over 60 days old), then your `models.json` field by field (`JsonLayers.Merge`; new keys are your models). `For` (priced), `Info` (any, for sizes) and `PricedAs` use the longest key the logged name contains, once per name and table. Files are checked for changes at most every 2 seconds.
- Models page (`ModelsView`, route `Models` or `Models:<name>`): two tabs, Catalog (the default; remembered in `state.json` as `ModelsTab`) and Compare (`ModelsView.Compare`: four type-ahead boxes, slots saved in `ComparedModels`, then a facts table with the best values marked, the radar and the Benchmarks card; a Catalog row's compare button fills the first free slot). Catalog: every model of the data and every one you added, with a provider filter and search; your values in the accent color (the data's value in the tooltip). Edit (`Dialogs.Model`) shows the values in use; a value equal to the data's, or empty, is not written, so models.json keeps only your differences (`ModelCatalog.Save`); a per-field Reset puts the data's value back, a row's Reset drops all your changes (or removes a model you added). The Usage page's model rows ("priced as …", "no price") and Add price open it with that model searched, or the Add dialog when the data has none.

## Levels
- System: managed or machine-wide folders (`level: "System"`, usually with `os`)
- User: folders under the home directory
- Project: `projectRoots`, resolved against each folder added in the UI

## Extension points
| Need | Change |
|---|---|
| New app or orchestrator | JSON entry, or "Add app" in the UI |
| New command or agent folder | a `parts` entry (`kind: "command"` or `"agent"`) |
| New skill layout | `ScanRoot.Layout` value handled in `Scanner.ReadRoot` |
| New plugin manifest | a `plugins` entry with an existing format (`folders` + `manifests`), or an `IPluginReader` implementation + register |
| New screen | class in `src/App/Ui`, add a nav button in `MainWindow` |
| New MCP config file | a `configs` entry (`kind: "mcp"` or `"settings"`); a new JSON key for servers goes in `McpServers` |
| New hook file | a `configs` entry (`kind: "hooks"`, a file or a folder of them; settings files are read for a `hooks` key too); a new shape goes in `Hooks.Parse` or a reader beside `Hooks.Kiro` |

## Screens
- Dashboard, Apps (list), app page (`App:<id>`), Plugins, Skills, MCP servers (`Mcp`), project page (`Project:<path>`), Health, Settings. `MainWindow.Go` routes and keeps back/forward history (Alt+←/→, mouse back/forward, and ← → buttons in the custom title bar, after the app name; F11 toggles full screen, no maximize button); views get a `Ctx`. The top bar shows where you are (the list part is clickable) and Search (Ctrl+K: pages, apps, projects, skills, plugins, actions). F5 rescans (on the Logs page: re-reads the files); Esc closes the bottom panel.
- Lists are flat tables (`Table.Build`), not trees.
- Project page: "Loaded into context" (below), Checks (below), the instruction/settings files, and the skills that apply in the project (that project's own rows + every User/System row) in the same list as the Skills page.
- Dashboard: tiles (apps, plugins, skills, health warnings) open their page; Plan & limits; plugins and skills by app (stacked by level) and by author (top 10 + Other; plugin manifest author, else SKILL.md `author`/`metadata.author`, else the marketplace; skills with none are "Local"); a bar opens the list filtered to it. "Changed since …" lists skills, plugins and config files added, removed or edited since the scan before (`ScanDiff`, saved as `cache/last-scan.json` in the data folder).
- Apps page: search, Status (All / Installed / Not found), category check boxes, Group by Category with collapsible headings (Expand all / Collapse all).

## Skills and Plugins pages
- `ItemBrowser`: full-width list (name, app link, level, invoked by or version, full path wrapped with the name part emphasized, row icons: open folder, copy path, remove). Search (`ItemSearch`, 150 ms after the last key): every word must match; name:, desc:, author:, app:, level:, keyword:/tag:, path: search one field (quoted: the whole value); ranked name, keywords, author, description, path; matches highlighted in name and description. One instance per page, so search, filters and selection are kept.
- Clicking a row opens `DetailPanel` at the bottom (drag the splitter to resize, the height is saved; double-click it to maximize; Esc or × closes). Left: description, app (link), invoked by, from, plugin, author, the other front matter, size (characters, ≈tokens, lines), checks. Right: Content (SKILL.md or a plugin's README rendered by `MarkdownView.Document`, or Source) and Files. Links to files inside the folder open in the panel with Back; folders open Files; web links open the browser; a link that leaves the folder asks, then opens that place in the file manager.
- Plugins: every app's plugins and extensions (Claude Code and Codex plugins, Gemini/Qwen extensions, Copilot CLI and Cursor plugins, Claude Desktop extensions, OpenCode plugins, Goose extensions, editor extensions, OpenClaw, Hermes, Zed, Factory). An app's `plugins` list names each place and its format (`PluginSource`); the level column shows its label (Extensions, npm). Version shown as is ("2.5.1"); the manifest gives description, author and keywords; "Contains" lists skills, commands and agents and flags hooks and MCP servers (they run programs). Disabled ones show "disabled". Add and Remove only where the app has `pluginCommands` (Claude Code).
- Commands & Agents (route `Part`, `LibraryView` kind "Part"): every Command and Agent row, standalone (an app's `parts` folders) or from a plugin (`PluginContents`: commands/ and agents/ plus the paths the manifest's "commands" and "agents" name, inside the plugin only; Source "App · plugin", `Plugin` set). Pills All / Commands / Agents; the From filter and grouping as for skills.
- Descriptions (skills, plugins) are one line of plain text (`MarkdownLite.Plain`): HTML and Markdown marks removed, entities decoded, YAML block descriptions read whole. Markdown files (`MarkdownView.Document`) turn their HTML into Markdown first (`MarkdownLite.FromHtml`: headings, bold/italic, links, images as alt text, lists, details/summary, tables, `<pre>`/`<code>`; comments, scripts and styles dropped; code fences and spans untouched; only known HTML tag names removed).

## Context per project (`ContextBudget`, `ContextSection`)
- One `IContextRule` per app (`context` in default/apps.json). Each returns the files the app reads in a project, in load order, with when they load (at launch, imported, on demand, matching files, agent decides, when mentioned, ignored), size and notes; `Start in…` picks the folder a session starts in.
- Claude Code: CLAUDE.md / .claude/CLAUDE.md / CLAUDE.local.md from the start folder and every folder above, user file and rules, managed policy, @imports (four hops; code spans, fences and quotes skipped; missing, repeated, too deep and outside-the-project imports reported), auto memory (first 200 lines or 25 KB), `.claude/rules` with `paths:` for matching files only, CLAUDE.md in sub-folders on demand. Warns above 40,000 characters.
- Codex: global AGENTS.override.md / AGENTS.md (not counted), then one file per folder from the git root to the start folder (override, AGENTS.md, `project_doc_fallback_filenames`), cut at `project_doc_max_bytes` (32 KiB default, from config.toml) — reported, since Codex cuts silently.
- Gemini CLI (context.fileName, @imports, sub-folders on demand), Copilot (copilot-instructions.md, nearest AGENTS.md, `.instructions.md` by `applyTo`), Cursor (.mdc by alwaysApply/globs/description; plain .md in .cursor/rules is ignored; 500-line guideline). No limit is shown where none is documented.
- Windsurf / Devin Desktop (global_rules.md; .devin/rules and .windsurf/rules by `trigger`; AGENTS.md, AGENTS.local.md, AGENT.md down to the start folder), Kiro (~/.kiro/steering and .kiro/steering by `inclusion`; AGENTS.md), Qwen Code (QWEN.md or `context.fileName` from ~/.qwen to the start folder, .qwen/QWEN.local.md, AGENTS.md), OpenCode (~/.config/opencode/AGENTS.md else ~/.claude/CLAUDE.md; the first AGENTS.md, else CLAUDE.md, going up; `instructions` paths and globs in opencode.json; web addresses noted, not read).
- Rule files that load only for matching files keep their patterns (`ContextFile.Patterns`, read with `Glob.Split`) so checks can test them.

- Window share: each app's header adds " · 0.4% of claude-opus-5-5's 1M window" for its launch tokens, with the model it used last (`UsageStats.LastModel`) and the model data's window; nothing when either is unknown.
## Project checks (`ProjectChecks`, `ProjectChecksSection`)
- Runs every context rule for the project, then: conditional rules whose patterns match no project file ("never loads"; `ProjectFiles.List` skips .git, node_modules, bin, obj and other build folders; skipped when the list is cut at 20,000 files); text an app loads twice at launch (two always/imported files sharing at least 8 lines of 12+ characters, or half the smaller file); empty instruction files; Markdown links to missing files (code skipped).
- Project and Local config files the apps define (`.mcp.json`, `.vscode/mcp.json`, `.claude/settings*.json`, `opencode.json`, …): invalid JSON; secret-looking values (known token shapes, or long values under key/token/secret/password names that are not `${VAR}`/`{env:…}` references or placeholders) reported by JSON path, never by value (info in personal Local files); `defaultMode: bypassPermissions`; `Bash`/`Bash(*)` allow rules.
- "MCP servers and hooks": every server (command + args, or URL) and hook command the config files start, with secret flags and values shown as `•••`; notes: not pinned (npx/uvx/bunx/pnpm dlx/docker run without a version, or `@latest`), env names, disabled.
- Personal files the apps read (Local config files such as `.claude/settings.local.json`, and `*.local.*` instruction files: CLAUDE.local.md, AGENTS.local.md, QWEN.local.md) that git does not ignore (`GitIgnore`: global excludes file, `.git/info/exclude`, `.gitignore` in each folder; last match wins, `!` takes back, `dir/` folders only, nothing comes back out of an ignored folder; files git already tracks are not looked up). Only in a git repository.
- Hooks that run a script (`HookScript`: skips runners such as bash, node, python, `uv run`, `pwsh -File`; fills `$CLAUDE_PROJECT_DIR` and `~`; skips anything with other variables) warn when the script does not exist.
- Shared files (`ProjectChecks.Shared`, info): CLAUDE.md, GEMINI.md or QWEN.md next to an AGENTS.md they never mention (suggests an `@AGENTS.md` line); apps with a context rule that read no file here while others do (one finding, naming the file each reads).
- Ignore files (config `kind: "ignore"`: `.cursorignore`, `.cursorindexingignore`, `.geminiignore`, `.codeiumignore`, `.continueignore`): `GitIgnore.Apply` counts the project files each hides (a table in the Checks card) and reports patterns that match nothing (info). Skipped when the file list is cut.
- Stale paths (info, `ProjectChecks.Paths`): code spans in instruction `.md` files that look like relative paths (a `/`, or a bare file name with a known lowercase ending) and exist neither from the project root nor the file's folder nor anywhere in the project; up to 5 per file. Fenced blocks, URLs, globs, placeholders (`path/to`), build folders and `Class.Member` look-alikes are skipped.

## AI folders and Claude Code settings (`AiFolders`, `ClaudeSettings`)
- `AiFolders.List`: the hidden top folders (`.claude`, `.cursor`, `.github` …) taken from the app definitions' project paths, only those that exist; apps that use each, what the scan found inside (commands, agents, skills, settings …), file count (stops at 2,000) and size. Shown with the project's commands and agents (user level included) on the project page.
- "Loaded into context" has a "By file" view (one row per file, one column per app, the short load mode in each cell) built from the reports already read.
- `ClaudeSettings.Read`: Claude Code's settings files in precedence order (System, Local, Project, User). Permission rules with notes (denied at another level, set to ask elsewhere, set at several levels); single settings (`defaultMode`, `model`, `enableAllProjectMcpServers`) with the winning level and what it overrides; list settings per level (directories, enabled and disabled MCP servers); `env` as names only; secret-looking values hidden.

- `ProjectChecks.ForHealth` adds the findings of every added project to Health (area Projects; a row opens the project page).

## Servers page: MCP and LSP (`McpServers`, `McpView`)
- Read with each scan from the scan's settings and MCP config files (every level, every project): `mcpServers` (Claude Code and Desktop, Cursor, Gemini, Qwen, Kiro, Windsurf, Copilot CLI, Roo), `servers` (VS Code), `mcp` (OpenCode), `context_servers` (Zed, also its older `command: { path, args, env }`), `projects.<path>.mcpServers` in `~/.claude.json` (Claude Code's local scope: level Local with that project), and Codex `[mcp_servers.*]` tables in config.toml (`McpServers.Toml`: strings, arrays over several lines, inline tables, booleans). YAML files (Goose, Continue) are not read; Goose extensions are on the Plugins page.
- Plugins (`McpServers.FromPlugins`, `.Plugins`): each plugin folder's `.mcp.json` and `.lsp.json` (`{ "mcpServers": … }` or the map itself), its manifest's `mcpServers` and `lspServers` (inline or paths inside the plugin), and an MCP bundle's `server.mcp_config`; rows carry `Plugin` and the plugin's app, level and project, and "plugin disabled" when it is off. Placeholders such as `${CLAUDE_PLUGIN_ROOT}` are shown as written. An `lsp` key in a config file (OpenCode, best effort) lists language servers.
- `McpServer.Kind`: "MCP" (tools for the model) or "LSP" (code intelligence for the agent). Pills All / MCP / LSP / Warnings; a Type column; Source is "from plugin X" (opens the plugin, `SourceCell`) above the file.
- Each row: name, app, level (with project), what runs (command line, or the address of a remote server), note, file. Secret-looking arguments, `key=` values and long random-looking runs in addresses show as `•••`. Notes: not pinned, key in plain text (env/headers values, arguments after `--token`-style flags, keys in the address), env names (first 4), disabled. Warnings (not pinned or a key in plain text) can be shown alone; a search box narrows the list.
- `~/.claude.json` is listed as a Claude Code config file with `appWritten`: Claude Code saves it on its own, so "Changed since" lists it only when added or removed.

## Hooks page (`Hooks`, `HooksView`)
- Read with each scan from every settings file (a top-level `hooks` key) and hook file (config `kind: "hooks"`, a file or a folder of `*.json` and `*.kiro.hook`) at every level, and from plugins (`hooks/hooks.json`, the manifest's `hooks`: paths inside the plugin or the hooks inline).
- One parser walks `hooks → event → [ … ]`, carrying `matcher` down into nested `hooks` arrays: Claude Code and Gemini CLI (`{ Event: [{ matcher, hooks: [{ type, command | prompt }] }] }`), Cursor (`.cursor/hooks.json`, `~/.cursor/hooks.json`: `{ version, hooks: { event: [{ command }] } }`), Copilot (`.github/hooks/*.json`, `~/.copilot/hooks`: `bash` and `powershell` variants, the one this system runs is shown). Kiro (`.kiro/hooks`: `.kiro.hook` with `when`/`then`, or the newer `.json` with `trigger`/`action`) is read best effort: its format changed in 1.0.
- Each row: event, matcher ("Every" when none or `*`), app, level, what runs (masked like servers) or the prompt's first line, note, source ("from plugin X" or the file). Relative scripts start from the project, a user hook file's own folder (Cursor runs `~/.cursor/hooks.json` there) or home; `${CLAUDE_PLUGIN_ROOT}` is filled for the check and shown as written. Warnings: a script that does not exist (`HookScript`), or download-and-run in one step (the `SafetyScan` rule); "disabled" and "plugin disabled" are noted.
- `ProjectChecks` uses the same parser for the project's settings and hook files (programs table and missing-script findings).

## Health (`Health`, `SkillCheck`)
- Each SKILL.md against agentskills.io: front matter present and closed, name 1–64 lowercase/hyphens and same as its folder, description 1–1,024, compatibility ≤ 500, body under 500 lines, links broken or leaving the folder, references that link on further.
- Claude Code's skill list: names + descriptions of skills the agent can load, against 1% of the context window of the model Claude Code used last (`UsageStats.LastModel`: the last model named in the final 256 KB of its newest log, found beside the scan), at about 4 characters per token (`SkillCheck.ClaudeListingBudget`; 8,000 characters, its documented fallback and 1% of a 200K window, when the model is unknown). Same skill name at several levels; plugins whose folder is missing, installed in several scopes, or with hooks / MCP servers. Projects: the context and project checks of every added project. Computed in the background after each scan; the nav shows the warning count.
- Safety (`SafetyScan`, area "Safety"): findings to review in skill folders (SKILL.md's folder; a flat skill file alone) and agent plugin folders (plugins that add skills, commands, agents, hooks or servers; editor extensions are skipped). Text files up to 512 KB each and 4 MB per item, at most 300 files. Rules: hidden Unicode (zero-width, direction control, tag characters; a leading BOM is fine), text that tells the agent to ignore earlier instructions or hide things from the user (prose files), download-and-run (`curl|sh`, `iwr|iex`, `DownloadString`, `-EncodedCommand`) as warnings; 200+ character encoded blocks (not embedded images), bare-IP and paste-site links, credential file names as information; a plugin's `hooks/hooks.json` that runs a script the plugin lacks (warning). Offline: nothing is run or fetched, and no finding does not mean safe. Results are cached per file by (path, size, modified time) and kept between runs in scan-cache.json (`ScanCache`, shared with the change fingerprints: paths, sizes, times, rule ids and hashes, never content), so a start reads only files that changed; a file with a line over 5,000 characters (minified) skips the text rules.
- Config files (`ConfigChecks`, area "Config files"): your User and System settings and MCP files that are JSON (TOML and YAML are not checked; files the app rewrites on its own are skipped): invalid JSON, secrets in plain text (information), `bypassPermissions` and `Bash(*)`, hooks that run a missing script. Values are never shown.
- Models (`ModelRetirement`, area "Models"): config files at any level (JSON and TOML) that pin a model retiring within a year: "Pins claude-sonnet-4-5, which retires 2026-11-30; use claude-sonnet-5-5. Source: …". Only the string values of keys whose name contains "model" are read; a provider prefix (`anthropic/`) is dropped and the longest model key the name contains is used (`ModelCatalog.InfoKey`). Retired or within `SoonDays` (90) is a warning, later is information.

## Change alerts (`ScanDiff`, `Fingerprint`)
- last-scan.json keeps, per skill, plugin, command, agent, config file, server and hook: kind, name, app, path, the file time (config files only) and a hash. Skills and agent plugins: SHA-256 over each file's path and content (files up to 256 KB by content, larger ones by size; 300 files, 4 MB per folder). Servers and hooks: SHA-256 of the definition's JSON as written (command, arguments, address, env, matcher). The content itself is never saved, so no secret reaches last-scan.json.
- "Changed since" lists Edited with what changed: "files changed", "version 1.2.0 → 1.3.0" (plugins), "command or address changed" (servers; a row opens the Servers page), "command changed" (hooks; a row opens the Hooks page). A new file time with the same content is no change. Entries written by an older version carry no hash: they never report an edit until the next scan has one.

## Export to AGENTS.md (`AgentsExport`, `ContextSection.Export`)
- "Export to AGENTS.md" in the "Loaded into context" header builds one file from the instruction files the apps load in the project (at launch, imported, matching files, agent-decided) that are inside the project, not personal (`*.local.*`) and not AGENTS.md. One "From <file>" section each: front matter removed, "Applies to: <globs>" for rules that load only for matching files, lines already written (12+ characters) and `@AGENTS.md` imports dropped, a header comment naming the sources and the date.
- A preview dialog shows the text first. A new file is created (never over an existing one); an existing AGENTS.md is copied to the backups folder and replaced, and the write is refused if the file changed after the preview opened. Then a rescan.

## Usage page (`UsageReport`, `UsageView`)
- One page for every app with a log or database the usage parsers read (`UsageStats.Supports`): last 7 or 30 days, read in the background once per scan and period. Tiles (input, output, cache read, estimated cost, sessions), per-day bars stacked by app (the top 4 apps, then Other; tokens without cache reads), a table by app (a row opens the app page) and by model. Cost is the app's own figure where its log has one, else an estimate from the model data (`ModelCatalog`); models without a price are left out of the cost. The per-app Usage card on an app page is unchanged (it also has per-project figures, accounts and live limits).

## Plan & limits (`LimitsService`, `LimitProviders`, `LimitsView`)
- Off by default per app; turning it on shows what is read and where it is sent. Refresh interval in Settings (minutes, at least 1); pages show the last reading (“Updated 40 s ago”) and request a refresh only when due; one call at a time per app. 401/403 → "sign in again" and no further calls until the credential file changes; 429 → waits (Retry-After, at most 15 min); offline → keeps the last reading. Expired tokens are not refreshed.
- Claude Code: `.credentials.json` → `GET api.anthropic.com/api/oauth/usage` (5-hour, weekly, per-model, extra usage; plan from subscriptionType/rateLimitTier). Codex: `rate_limits` in its session logs (no network); with live limits on and the log older than 10 min, `GET chatgpt.com/backend-api/wham/usage`. Copilot: Copilot CLI config.json or editor apps.json token → `GET api.github.com/copilot_internal/user`. Cursor: state.vscdb (read-only) → `cursor.com/api/usage-summary` (shape not published: only recognized figures are shown). Gemini CLI: oauth_creds.json → cloudcode-pa loadCodeAssist + retrieveUserQuota. All undocumented: replies are read leniently.
- "Full about HH:mm at this pace" from the rise between two readings.

## Changing things
- Skills: `SkillManager.Install` copies a folder with `SKILL.md`; `SkillManager.Remove` moves it to `~/.ai-stackprint/backups/skills/<timestamp>/`. System-level and plugin-provided skills cannot be removed here.
- Plugins: `PluginManager` runs `pluginCommands` from the app definition (Claude Code: `claude plugin install|uninstall`) and shows the output.
- Apps: `AppCatalog.SaveUser` adds a custom app (refused for a built-in id or name); `AppCatalog.RemoveUser` deletes a custom entry from `apps.json`; `settings.json` holds hidden apps.

## Export and import (`DataExport`, `DataImport`, `TransferSection`)
- Export: tick Settings, Models, Apps, Projects; "Only my changes" (the default: settings that differ from defaults, your model overrides, custom apps) or "All values" (every setting, every model as this version has it). One JSON file `{version, exported, values, settings, models, apps, projects}`; paths under the home folder are written as `~/`. No state, caches, logs or secrets.
- Import: `Plan` reads the file and refuses invalid JSON, a file that is not an export and a newer `version`. The preview lists each change (now → imported), project folders that do not exist here (Locate… or skipped) and notes. `limitsEnabled` and `checkUpdates` are never imported. `Apply` copies each file it will write to `backups/import-<time>/` first, then merges: imported values go over yours, and only values that differ from defaults or the model data are saved. A custom app whose id or name is built in now is left out. Then the app reloads settings, apps and projects and rescans.

## Viewing and editing files
- `CodeView` wraps AvaloniaEdit with TextMate grammars (json, markdown, yaml, ini for toml, log). Light+/Dark+ follows the app theme.
- Config files: read-only until Edit; Save validates JSON (comments/trailing commas allowed; other formats unchecked), refuses if the file changed since it was opened, copies the original to `~/.ai-stackprint/backups/configs/<timestamp>/`, keeps the BOM choice. Files over 2 MB stay read-only.
- Logs page (`Logs:<id>`):
  - Summary (7 d / 30 d / all): files, size, activity, error/warning lines, and for session logs sessions, prompts, tool calls, top tools, sub-agents, tokens, models. Computed in the background; parsed sessions cached by path+size+time.
  - Files: newest first; delete one, selected, or "older than 7/30/90 days" → Recycle Bin (Windows) or Trash (macOS `~/.Trash`, Linux freedesktop Trash). Only files the app listed can be deleted; recently modified files and session logs get a warning.
  - Watcher (`LogFolderWatcher`): the selected app's log folders (by pattern, sub-folders when the source has depth), events batched for 250 ms, plus a 10 s stat of the newest file. New, removed or renamed files find the list again; a file that grows gets its size and time updated in place. Leaving the Logs page releases the viewer, summary, watcher and grammars and compacts memory. The open file reloads when Follow is on; otherwise a "New lines" button appears. New steps (Conversation) get an amber fill behind the text and a solid ring (Raw: amber lines) that fade out over Settings › Appearance › New log lines (default 10 s, 0–60, 0 = off; `fadeSeconds` in settings.json).
  - Viewer toolbar: search, Follow, Raw/Conversation, open file, open folder. No Reload (F5 reads again); the header says only when part of a large file is left out (size and time are in the file list).
  - Conversation: everything reads left to right; the assistant's messages leave 20 px free on the right, yours are indented 20 px from the left. A step whose opened text would equal its one-line header has no arrow.
  - Text in the Conversation view goes through `TextDecode.Prepare`: JSON (also inside a JSON string) pretty-printed, `\uXXXX`/`\n` escapes decoded, ANSI shell colors shown as colored runs (palette follows the theme), inline image data shortened; a "Show original" button undoes it per step.
  - Viewer: Raw = last 256 KB in `CodeView` (line numbers optional, off by default). Conversation = the last 8 MB streamed and parsed by an `ILogParser`; code fences, tool inputs and tool results are highlighted (results by the file a Read returned, or JSON/diff detection), built lazily when expanded.
  - Search covers the whole file (case, regex, "only matching lines"); results list with line numbers; clicking jumps to the line, loading the part of the file around it when it is outside the tail.

## Performance
- `AiStackprint --perf` (or `dotnet run --project src/App -c Release -- --perf`) starts as usual, then after the first scan opens every page in turn (Apps, the first installed app, Plugins, Skills, MCP servers, Usage, Logs, Health, the first project, Settings, Logs again, Dashboard) and closes. For each it records the time to build on the UI thread, the time until no loading icon is left (`Busy.Class` on every spinner), the CPU time used and the managed heap and working set after a full collection; plus launch (process start to window), the first scan with each step (cache load, collect, mcp, changes, health, safety, configs, cache save) and start (launch to a complete dashboard).
- Rows are appended to `~/.ai-stackprint/logs/perf.log` (CSV: time, version, page, build_ms, ready_ms, cpu_ms, heap_mb, working_set_mb; page names only, no paths or content) and `perf-report.txt` shows the last run beside the one before, with the change in ready time. Run it twice before and after a change: the first start after a build reads files cold, and times vary by 10-20% between runs.
- Found this way: `SkillDoc.Read` sized its buffer to the 512 K limit (1 MB per skill, a full collection every few skills: the health step took 1.2 s instead of 0.2 s); folder listings carry each file's time so cache stamps need no extra call; `ScanCache.Save` writes only when a file was read; the usage card parsed every log twice.
- Session logs are read as UTF-8 lines (`LogReader.Utf8Lines`) and parsed as JSON straight from the bytes: no decoding to text and back, about half the time and a fifth of the allocations. `LogParsers.Json` hands out each line's element only until the next line (its document then goes back to the pool). The Logs summary counts with `ILogParser.Count` (the same numbers as `Parse`, without building the steps' text) over several files at once (at most 4).
- Pages are rebuilt on every visit and the old one must become garbage. Views live as long as the window and keep some controls in fields (search boxes, filter boxes, hosts that async work fills) and callbacks that capture page controls. Avalonia keeps a removed control linked to its old page's drawing (composition) tree, so one such control keeps that whole page in memory: after a visit to Skills, about 50 MB. So when another page opens, `MainWindow.Leave` calls the view's `Leave()`, which swaps those controls for new ones (texts, filters and selection are plain fields and stay) and drops callbacks into the page (`ItemBrowser`, `SkillFilter`, `DetailPanel`, `AppsView`, `McpView`, `UsageView`, `ProjectView` and its sections; Logs has `Release`). A refresh of the same page keeps them. `OnPause` reports only real changes and nothing after its box left the window, so a pause timer cannot rebuild a page that is gone. `PagesTests` checks that a left Skills page is collected.
- Prices are looked up once per model name and price table (`ModelCatalog.For`; changed model files make a new table): costs are asked for every usage event, and the scan for the longest matching key grew with the table (100k costs: 0.45 s with 200 models, 2.5 s with 2,000, 34 MB each); now about 8 ms and no allocations at any size.
- A publish for one platform (`-r <rid>`: the installers and the plain publish) is ReadyToRun (`PublishReadyToRun` in the app project): the app and library DLLs carry machine code next to their IL, so startup and first page visits need little JIT. Measured with `--perf` (win-x64, self-contained, 4 runs each): the window opens in 0.9 s instead of 1.7 s, the dashboard is complete in 2.1 s instead of 2.9 s, the first Skills visit takes 0.4 s instead of 0.8 s; the download grows about 8 MB (75 → 83 MB zipped), installed files about 18 MB. `dotnet run` and `dotnet build` are not ReadyToRun, so compare perf runs from published builds only.
- The startup scan does only what the dashboard needs, and runs its independent checks side by side (changes, health, safety, configs; each step's `--perf` time is its own). The projects' checks (`ProjectChecks.ForHealth`, which walk every project folder) run after the dashboard shows: the Health tile, the badge and the Health page wait for them with a loading icon (`AppState.ProjectHealth`). A page that is not shown loads nothing.
- Project folders are listed with one native pass (`ProjectFiles.Walk`, `FileSystemEnumerable`; 4 times faster than a call per folder) and the list is kept for 30 seconds, or until the next scan (`ProjectFiles.Forget`), because several checks ask for it. `ContextBudget.Below` reads each folder's file names once instead of a stat call per name, and the start folders of a project (`ProjectChecks.Nested`) are read side by side. On a project with 20,000 files this took the project checks from 1.8 s to 0.7 s.
- Long lists build only the rows on screen, short ones build every row: `Table.Virtual(cols, rowMakers, empty)` builds a normal table when the list has at most `Table.VirtualFrom` rows (the setting `virtualListRows` in settings.json, default 40, not on the Settings page; 0 = every list is virtual; measured on the skill rows: up to about 10 rows the two cost the same, from about 30 rows the virtual list is smaller and faster, at 60 rows 39 ms and 5 MB against 83 ms and 21 MB) and otherwise puts a `VirtualRows` panel in the page's own scroll viewer (the Skills, Plugins and Commands pages, an app's skills, the project page lists and the Models page). A row's controls are made when it comes within about 480 px of the visible part (`EffectiveViewportChanged`) and thrown away when it is far; heights are measured once, unseen rows count with the average, and the scroll position is adjusted when a row above the screen turns out another height than guessed. 263 skills hold about 17 to 32 rows of controls (754 controls instead of 8,500); the heap with the Skills page open went from about 70 MB to 8 MB in a test, and in the `--perf` run Skills 88 MB to 26 MB, the project page 120 MB to 58 MB. A row's maker is a `Func<TableRow>`: `SkillFilter.RowMakers`. `Table.Build(..., batch)` (rows built in batches after the page is drawn) stays for tables that are long but not big enough to need this.
- The startup scan reads each app on its own thread (`Scanner.Collect` runs `CollectApp` per app with PLINQ, `AsOrdered`, so the result keeps the apps' order): in a `dotnet run` build (Release, `--perf`) the collect step went from 876 ms to 349 ms, the scan from 1.54 s to 0.97 s and start (launch to a complete dashboard) from 3.96 s to 3.35 s. Each app only reads files; keep it that way (no shared lists or statics in the readers). The installed font list of Settings › Appearance is read once (`AppearanceSection._installed`).
- Memory: a shown control costs about 8 KB of heap (text layouts), so what matters is how many controls a page holds; a page that is left is released (checked with a weak reference), and `MemoryTrim` hands the memory back to the system 2 s after the last page change. GC settings (gen0 size, conserve memory) made no difference in the `--perf` run; the working set at start (about 300 MB with a 22 MB heap) is mostly the runtime, Avalonia and Skia, and a ReadyToRun publish is about 30 MB lower and starts about twice as fast as `dotnet run`.

- Date and time: what the app keeps is UTC (`state.json` times are `*Utc`, a project's `added`, the last-scan snapshot, internal clocks); times that come from outside (log lines, limit resets, file times) are converted to local time when read and shown as local time with no zone, in `yyyy-MM-dd HH:mm`; a date without a time (a model's retirement, the model data date) is a plain `yyyy-MM-dd` and picked in a date picker. `crash.log` lines carry the offset (`+07:00`) so a report is not ambiguous. File names of backups use local time.

## Crashes
`CrashLog` writes any error that closes the app (and failed background work nobody waited for) to `~/.ai-stackprint/logs/crash.log`, with the version and OS; it does not keep the app running. On the next start `CrashNotice` shows a card once: Report on GitHub opens a prefilled new-issue page (`CrashReport`: last entry, home folder and user name removed, cut to fit the link); the user submits it in the browser, the app sends nothing.

## Usage card (app detail page)
- `UsageCard` appears for apps whose session logs have a usage parser (`ILogParser.Usage`: Claude Code, Codex; `ILogParser.UsageFile` for a database: OpenCode). It shows tokens by type (input, output, cache write, cache read), an estimated cost, a per-day chart (tokens or cost, last 90 days at most), and totals by model and by project, for 7 days / 30 days / all.
- `UsageStats` reads each file once (newest 8 MB, streamed as UTF-8 lines) into small per-day buckets plus its last 8 days of events, cached by path + size + time; the card's totals and `Live` share that one read. Only lines that can carry usage are parsed as JSON (Claude Code: lines with `"usage"`; Codex: session_meta, turn_context, token_count). Claude Code replies that are written on several lines are counted once (message id + request id). Codex totals are running counters, so each event is the difference from the one before.
- OpenCode (`OpenCodeUsage`, read-only SQLite): one event per assistant message in `message`, and one per session in `session_v2` (newer versions keep no per-message tokens). Its output excludes reasoning, so reasoning is added to output. Its own `cost` is used when above 0 (0 also means "no price in OpenCode"), else the model data.
- Cost: `ModelCatalog` (see Model data). USD per 1M tokens; a model gets the price of the longest key its name contains; models without a price show tokens only; an unknown cache price counts at the input price (a 1-hour one at the short-cache price). Buckets are split by what changes the price (`UsageBucket.Tier`, `Fast`, `UsOnly`; `CacheWrite1h` and `WebSearches` are counted in them): a reply whose input (input + cache read + cache write) is over a tier's `tokens` is priced at that tier, a field the tier leaves out at the base price; fast mode and US-only processing multiply by `multipliers.fast` / `.us`; web searches add `webSearch` each (a tile of their own). Prices are applied when shown; the tier is fixed when a log is read, so the usage cache key includes every model's thresholds (`ModelTable.TierKey`) and changed thresholds read the logs again. Claude gives these per reply (`cache_creation.ephemeral_1h_input_tokens`, `speed`, `inference_geo`, `server_tool_use.web_search_requests`); each Codex `token_count` event is one reply (checked on real logs: its `last_token_usage` equals the change in the running total), so its input picks the tier. Prices are estimates from public list prices, so check them.
- A model row opens it on the Models page ("priced as …" or "no price" under the name); Add price opens the Add dialog for the first model without a price. An empty price is still unknown (0 means free). The chart uses its own theme keys (`Ap.ChartIn/Out/Write/Read`) so series differ in light and dark.
- Limits (top of the card): `UsageStats.Live` gives use in the last 5 hours / 7 days and the current 5-hour block (a block starts at the first message after a 5-hour gap, on the hour). `ILogParser.Limits` returns percent used and reset time when the app logs them (Codex `rate_limits`); Claude Code does not log them, so only use is shown.

## Conversation view extras
- Peak context (`Session.PeakContext`, `ContextWindow`): the largest request of the main conversation (Claude: input + cache read + cache write per reply, sub-agents left out; Codex: `last_token_usage.input_tokens`), shown in the session summary as "Peak context 312K of 1M (31%)" against the window Codex logs (`model_context_window`) or the model data's.
- `ContextBlocks` splits injected text (`<INSTRUCTIONS>`, `<environment_context>`, `<system-reminder>`, `<!-- name:begin -->…<!-- name:end -->`) into collapsed "Injected" areas inside the message. `MarkdownLite` + `MarkdownView` render headings, lists, quotes, rules, tables and bold/italic/code/links as selectable text; code fences still use `CodeView`.
- `AgentTimelines` + `AgentGraph` draw a lane per sub-agent (Claude: `agentId`) with the branch and merge points and the periods the main session waits. `LogEntry.Agent` carries the id.
- Plain `Txt` text is not selectable; right-click copies it (`MainWindow.CopyMenu`). Use `W.Sel` for text outside click targets (detail panels).
- Skills / Plugins pages and an app's Skills section: level check boxes (all checked by default); skills also Invoked by as one choice (All, Agent only, User only, Agent and User, with counts that follow the level and source filters), From and Group by (Invoked by / From / both, collapsible headings). The last checked box cannot be unchecked. Only values present are offered; a filter with one value is left out; filters reset when another app opens. UI in `SkillFilter`, rules in `SkillMatch`.
- Who can invoke a skill is a list (`Item.Invokers`: Agent and/or User from SKILL.md front matter), shown as "Agent only", "User only" or "Agent and User" in the filter, table and group headings.
- Apps page: category check boxes (plural labels, counts follow the search), kept while the app runs.
- Rule: one value per item (level, category) → check boxes; a combination per item (invoked by) → one choice. Filter rows use `FilterRow` (fixed-width label column).
- Alignment: `Row()` centers its children vertically; `Pills()` spaces with the panel (one line is 32 px); `SearchBox()` centers text and icon.
- Dots beside text (`WithDot`: level, chips, legends) are an inline of the TextBlock standing on the baseline, so they line up with the letters.
